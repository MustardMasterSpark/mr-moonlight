3. WHERE TO ACTUALLY LOOK, IN ORDER
==============================================================================

1. **Input system split — read this before wiring Escape/Pause input.** Per
   `Docs/mrm9-hqfps-integration.md` §10 item 8 (still open, unresolved): `InputMapController`
   (ours) clones the project's Input Action asset; HQ FPS Weapons' `InputManager` binds the action
   asset directly. They currently coexist, but **pause/UI input modes don't cover FPSCore's
   actions** — this is exactly the gap a pause feature will fall into. Check both systems' current
   action maps before adding a new binding; a naive new "Pause" action on only one of them will
   silently not fire depending on which system currently "owns" input focus. Confirm current state
   via UnityMCP before assuming this doc entry is still accurate (memory-staleness rule).
2. **Reuse the Death sequence's halt/fade patterns.** MRM-17 ("Death sequence + blackout") is Done
   and already solves "remove all control immediately, clean up HUD state, fade to black" —
   `DeathSequence`, `HealthRedTintSource`, `PlayerDamageReceiver` on
   `Player_Tracey/MrMoonlight Systems`. Pause needs the same "freeze player input, don't freeze UI
   input" split. Read `DeathSequence.cs` first rather than designing pause halt logic from scratch.
3. **Static-registry gotcha already hit once** (MRM-11 traps memory): a static `ScreenTint`
   registry not cleared between scene loads caused a stuck red tint after death, fixed in build 23.
   If pause's fade-to-black reuses any similar static/singleton screen-effect registry, check it
   clears on Restart/Return-to-Menu, not just on normal unpause.
4. **HUD Canvas** (`HUD Canvas` GameObject in `Island.unity`) already exists with `EventSystem` +
   `InputSystemUIInputModule` present in the scene (confirmed working, MRM-11 traps memory: the
   scene originally had NO EventSystem and UI buttons were silently dead — that's fixed now, but
   verify it's still there before assuming pause UI buttons will just work).
5. **Checkpoint system status:** per MRM-19's own acceptance criteria, "Restart from last
   checkpoint" needs an actual checkpoint system Carlos hasn't designed yet. Do not invent one;
   leave the placeholder method the issue explicitly asks for, same as the Game Over screen's
   equivalent placeholder.
6. **Time.timeScale vs a dedicated pause flag:** decide and document (per MRM-19 acceptance
   criteria: "pausing during a cutscene either works correctly or is blocked deliberately"). Check
   whether `EventDirector` (the text-script level-flow system from MRM-11) has any timing
   assumptions that would break under `Time.timeScale = 0` — likely does, since it's driving
   scripted `wait` blocks. This needs a decision, not just a `Time.timeScale = 0` reflex.
