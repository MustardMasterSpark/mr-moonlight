TRAPS ALREADY KNOWN IN THIS EXACT AREA
===============================================================================
- **FadeOverlay sibling order matters.** It was originally the FIRST child under Canvas, which in
  Unity UI means it rendered BEHIND everything else - the "opaque black screen" wasn't actually
  covering the menu. Already fixed (moved to last/topmost sibling), but if a new title-screen
  object gets added as a Canvas child directly (rather than as a child of FadeOverlay, like the
  existing cards are), re-check sibling order before assuming it's on top.
- **This whole sequence has never been watched end-to-end by an automated session.** The Editor
  doesn't tick Update()/coroutines while its window is unfocused (project-wide limitation, see
  memory `verification_requires_a_build`), and the sequence + fade + feather-fall intro combined
  runs longer than any headless verification window tried so far. Confirmed logically correct by
  reading code/component wiring, never confirmed by actually watching it play. If Carlos hasn't
  personally watched the current 2-card version play start-to-finish, that's worth doing BEFORE
  adding more cards on top, so any timing/ordering issue is caught before it compounds.
- **Play Mode discards scripted edits on stop.** If tuning card fade/hold timing or text live in
  Play Mode (natural way to iterate on this), remember every such edit vanishes the instant Play
  stops unless re-applied in Edit Mode afterward and saved. Hit this twice in the immediately-prior
  session (rain rate, ripple tuner values) - see `[[unity_playmode_edits_discarded_on_stop]]` in
  memory. Always re-verify `Application.isPlaying == false` before an edit you need to persist, and
  re-check the value stuck after Carlos stops Play before calling anything final.
- **CRT post-process filter is scoped to MainMenu already** (`GlobalVolume_CRT`) and Screen Space -
  Overlay canvases are structurally exempt from post-processing in Unity (composited after the
  camera finishes) - so title-screen UI will never pick up scanline/CRT distortion regardless of
  Canvas hierarchy. Not a bug to chase if a title card looks "too clean" next to the CRT-filtered
  3D background behind it - that's expected, matches how the existing menu buttons/credits already
  behave.
