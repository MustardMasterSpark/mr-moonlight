TRAPS ALREADY FOUND

- **Prefab-to-instance propagation is not reliable for structural component changes.** Editing
  `Enemy_Spotter.prefab` via `PrefabUtility.LoadPrefabContents` + `SaveAsPrefabAsset` does not
  always auto-sync already-placed scene instances when you destroy one component type and add
  another on an existing child object. First pass this session: 1 of 102 instances (the
  earliest-placed one) stayed on stale components after a full scene reload and needed the fix
  applied to it directly. Second pass: 0 stragglers. Not predictable which instance sticks —
  **always verify every placed instance after this kind of edit**
  (`GetComponentsInChildren(typeof(EnemyHitbox), true).Length` across every child of "Enemies", not
  a spot-check on one).
- `manage_scene`'s `load` action can refuse with "unsaved changes" immediately after a successful
  `save` — something in this scene re-dirties itself every tick even at rest (unidentified,
  SunController/TimeManager are candidates). Reload via
  `EditorSceneManager.OpenScene(path, OpenSceneMode.Single)` in `execute_code` directly instead of
  fighting the guard.
- `mcp__UnityMCP__execute_code` has no Roslyn installed — it silently falls back to CodeDom (C# 6):
  no `using` statements inside the code body, no tuples, fully-qualify anything outside
  `UnityEngine`/`UnityEditor` (e.g. `UnityEngine.AI.NavMesh`), and one call's local variables do not
  persist to the next call. Full detail if you hit a confusing compile error: this file's sibling
  memory note (not in this repo — ask if you want the details re-derived here instead).
