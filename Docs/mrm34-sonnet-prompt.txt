TASK 1 — VERIFY THE HIT-LOOP FIX (do this first, before anything else)

Carlos reported: "I hit the enemy once and then he looped in his stunned animation."

Root cause was found and fixed but NOT watched running. The fix is
EnemyHealth.ResolveAttacker() — it walks a damage source up to transform.root
before handing it to blaze.Hit(), because Blaze rejects any enemy whose tag is not
in vision.hostileTags, and the gun was passing the untagged "Arms" child.

Full chain is documented in section 15.1. Go and confirm it actually works:
shoot a Spotter once, check he flinches and then resumes rather than sticking.

If he STILL sticks, the next suspect is section 15.2: EnemyRangedAttack.RunBurst()
is a coroutine that keeps driving the animator through the flinch. CancelBurst()
already exists and is wired to EnemyHealth.Died but not to the hit. Wire it to
TakeDamage or to HitStateBehaviour.onStateEnter. Change ONE thing at a time.

HOW TO TEST

The player cannot deal damage in the normal way (MRM-32 is Backlog), so use the
debug tools that exist for exactly this:

  - EnemyDebugControls on Enemy_Spotter. In play mode, right-click the component's
    header in the Inspector (or the three-dots icon): Damage / Kill / Attack Player
    / Fire Flare Now / Log State. Start with Log State.
  - F4 on the player toggles invulnerability. It blocks the damage but still counts
    and displays every hit on screen, so you can watch a whole fight without dying
    and still see that shots are landing. F3 is infinite stamina.

CRITICAL: play mode only ticks while the Unity editor window has focus. If
Time.time is frozen at 0.02, the editor is unfocused — ask Carlos to click into
Unity. Do not burn calls rediscovering this. Also: a PlayerSettings change made
DURING play mode is reverted on exit.


TRAPS THAT HAVE ALREADY COST TIME (all in the doc, do not rediscover them)

  - Blaze identifies things BY TAG, and the tag must be on the object that carries
    the collider, not a parent. This caused both bugs fixed today.
  - A BlazeBehaviour subclass REPLACES a state slot; it cannot run alongside one.
    For a new interrupting state use BlazeAISpareState / blaze.SetSpareState().
  - AddComponent<BlazeAI>() leaves vision and waypoints NULL. If you build an agent
    from script you must new them.
  - GetComponentInParent<T>() skips inactive GameObjects, and a prefab ASSET counts
    as inactive. Verify wiring against the live scene instance.
  - RetroLit materials: the KeywordEnum properties need SetInteger AND the matching
    keyword toggled. Cloning a known-good .mat is the safe way. See
    Docs/3d-prop-pipeline-wizard.md section 3.2.
  - Anything both Burntwax and our code must see has to live in MrMoonlight.Combat
    or another leaf assembly — MrMoonlight.Runtime already references Burntwax.Core,
    so the reverse is a circular reference.
