### 2. First Unity import — found and fixed three real pipeline bugs
All three are now written back into `Docs/3d-prop-pipeline-wizard.md` (§0 ground-rules table,
new §4.2a) so they don't recur:

1. **`import_model_file` silently set Scale Factor to 0.556 and Materials to LegacyImport.**
   Ground rule says Scale Factor 1 / Materials None — always check and fix these after using that
   tool, don't trust its defaults.
2. **Object had an unapplied Rotation X=90°/Scale 0.01 in Blender** (visually fine because the
   object transform was compensating for un-applied mesh data). Carlos applied transforms —
   fixed, verified numerically in Blender: `dimensions = (1.53, 0.41, 1.80)`, origin at feet,
   rotation/scale/location all identity.
3. **The real find:** even with a clean Blender-side export, Blender's default FBX axis settings
   (`-Z Forward`, `Y Up`, `bake_space_transform=False` — the exporter's own default, matches what
   Carlos's dialog showed) left the Z-up→Y-up conversion as a transform-level correction. Unity
   imported it with a **non-identity root rotation** (~90° on X) instead of baking the conversion
   into the mesh. `ModelImporter.bakeAxisConversion = true` did **not** fix this for a plain mesh
   with no Animator/Avatar. The fix that worked **for now (no armature yet)**:
   `bake_space_transform=True` on export (the exporter's "Apply Transform" checkbox) — bakes the
   rotation into vertices, so Unity's root reads clean identity. **This will need to flip once
   AccuRig adds a rig** — `bake_space_transform` is unsafe for rigged content; at that point use
   `ModelImporter.bakeAxisConversion` on the Unity side instead. **Not yet validated on a rigged
   export** — test this for real on the first AccuRig re-export, and correct §4.2a if
   `bakeAxisConversion` doesn't behave as documented for a Humanoid/Generic avatar.

### 4. Blaze AI research — grounded in the real API, not guessed
Read `CoverShooterBehaviour.cs` directly (`E:\playground\My project\Assets\PLAYGROUND\Blaze AI
Engine\Scripts\Behaviours\CoverShooterBehaviour.cs`). Key facts for whoever wires this next:

- Blaze drives animation by **string clip name per field**, not Animator parameters:
  `idleAnim`, `moveAnim`, `equipAnim`/`unequipAnim`, `shootingAnim`, `moveForwardsAnim`/
  `moveBackwardsAnim`, `leftStrafeAnim`/`rightStrafeAnim`, `searchPointAnim`, `endSearchAnim`,
  `returnPatrolAnim`. Played via `blaze.animManager.Play(name, transitionTime)`.
- **Minimum clip set for a first working pass:** Idle, Walk, Equip, Unequip, Shoot, Death.
  Everything else (strafe, forward/backward-while-aiming, search) can stay blank — Blaze just
  skips that sub-behavior.
- `shootEvent` (a `UnityEvent`) is the hook point for actual weapon fire (muzzle flash, damage,
  the flare projectile) — wire our own method there, don't reimplement Blaze's shot cadence.
- **The flare mechanic is NOT a Blaze field** — MRM-34 confirms this stays a custom
  `BlazeBehaviour` subclass (same shape as `GoingToCoverBehaviour`/`CoverShooterBehaviour`
  — `Open()`/`Close()`/`Main()` virtual methods). Not yet written.
- Going-to-cover is a separate `GoingToCoverBehaviour` component + `BlazeAICoverManager`,
  already shipped, not yet inspected in detail — do that before wiring cover.
