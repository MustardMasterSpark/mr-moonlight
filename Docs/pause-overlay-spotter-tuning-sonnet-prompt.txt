TRAPS HIT AND FIXED — READ BEFORE TOUCHING THIS AGAIN:

1. **`Awake()` does not fire on a GameObject that starts inactive.** First version of
   `PauseOverlayUI` resolved `root = gameObject` in `Awake()` as a fallback when the inspector
   field was left empty — same pattern `GameOverPanel.cs` uses. But this object starts disabled
   in the scene (hidden until Show() is called), so Unity never calls Awake on it, `root` stayed
   null, and the first live Pause() threw `UnassignedReferenceException`. Fixed by making `root`
   a lazily-resolved property instead (`root != null ? root : (root = gameObject)`), so it never
   depends on Awake having run. If you ever see this exact exception on a hidden-by-default UI
   panel, this is almost certainly why — check whether the object starts active.
2. **`TextureImporter` default max size in this project is 512, not Unity's usual 2048.**
   Importing `controls.png` (a 3840x2160 source) at default settings silently downscaled it to
   512x288 — that's the actual cause of "pixelated," not the display size. Fixed by explicitly
   setting `maxTextureSize = 2048` on both the Default platform settings AND an explicit
   Standalone override (`overridden = true`) via `TextureImporter`/`SaveAndReimport()` — a plain
   `manage_asset modify` properties dict did not touch this, had to go through
   `execute_code`/`TextureImporterPlatformSettings` directly. **If any other recent UI/prop
   texture import in this project looks soft, check its max size the same way — this may not be
   a one-off.**
3. Sizing was switched from a fixed pixel `sizeDelta` (1152x648, my first guess) to anchor-based
   sizing (`0.03,0.03`-`0.97,0.97`) once Carlos's marked-up screenshot showed he wanted it much
   bigger (~94% of the screen). Anchors work here specifically because the canvas is authored at
   16:9 (1920x1080) and the source image is also 16:9 — a uniform anchor margin on all four sides
   scales both dimensions by the same ratio, so it doesn't distort. `preserveAspect = true` stays
   on as a second line of defense regardless.

TRAP HIT — READ BEFORE CHANGING ANY MoonlightTunables VALUE AGAIN:

**`MoonlightTunables` is a ScriptableObject with an already-serialized asset
(`Assets/_Project/Data/Resources/MoonlightTunables.asset`), and Unity does NOT re-apply a
changed C# field default to a field that's already been serialized into that asset.** Editing
the `= 100f` in the class to `= 65f` alone would have done nothing at runtime — the asset had an
explicit `SpotterPopulationSpawnRadius: 100` line already written. Every tunable edit in this
project needs the asset itself updated too (via `SerializedObject`/`SaveAndReimport`-style code
through UnityMCP's `execute_code`, or by hand in the Inspector) — check
`Assets/_Project/Data/Resources/MoonlightTunables.asset` for the field name before assuming a
code-only change took effect. Corollary discovered along the way: the whole Relocation/
Aggression tunable block (added by the previous session) had never actually been serialized into
this asset at all — it was silently running on C# defaults this whole time. All of it (kill
thresholds, population bonuses, tiered check intervals) is now explicitly written into the asset
too, matching the values documented in `Docs/spotter-relocation-aggression-sonnet-prompt.txt`.
