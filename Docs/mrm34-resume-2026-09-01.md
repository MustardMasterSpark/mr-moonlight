## 1. The real gap: the shared groundwork MRM-34 depends on doesn't exist yet

MRM-34's own issue text assumes Blaze's `CoverShooterBehaviour` + `GoingToCoverBehaviour` +
`Vision.cs` + `Waypoints.cs` cover most of patrol/chase/vision/navigation for free. That's true of
the **package's capability**, but the **project's own setup work** to actually use it hasn't
happened:

- **MRM-27 (NavMesh + Blaze on sloped terrain) — still Backlog.** No `NavMeshSurface` baked, no
  bound-to-walkable-area setup, Blaze's `Tags&Layers.preset` never applied (⚠️ its own text warns
  this must happen first and the before/after layer diff recorded — layer order is load-bearing
  for terrain splatmaps and footstep surfaces, see `unity_layers_state` memory for current
  layer/tag state to diff against). **Open question, unresolved in the issue itself:** do terrain
  trees rasterize as NavMesh obstacles, or do they silently pass through the way they reject
  MeshColliders elsewhere in this project (`webgl_gles3_gotchas` memory)? Bake early and check —
  don't assume either way.
- **MRM-29 (shared idle/patrol/chase/search state machine) — still Backlog.** Blaze covers idle/
  patrol/chase/vision/waypoints natively; what's genuinely still ours is the **three-blind-run
  search behaviour** (180° → 360° → free, with the originally-static-vs-originally-patrolling
  return rule) as a `BlazeBehaviour` subclass. This is explicitly the *pattern* every enemy
  behaviour (Spotter's flare, later Zealot/Wolf) is supposed to follow — read MRM-29's full issue
  body for the exact state chart before writing the Spotter's own `BlazeBehaviour` subclasses, so
  the pattern is consistent from the start rather than retrofitted.
- **MRM-28 (vision cones) — still Backlog, and likely stale.** Blaze's own `Vision.cs` probably
  covers the enemy-side scope already (separate cone angle + sight range per Normal/Alert/Attack
  state) — see the gap comment posted on it. What's NOT covered is the **player's own vision cone**
  (for the Zealot's "is Tracey looking at me" check) — not needed for Spotter, but don't duplicate
  Blaze's cone system from scratch for the Spotter without checking this first.

**Decision needed before starting:** does this session build a minimal working slice of MRM-27 +
MRM-29's shared pattern as part of this same branch (mirroring how MRM-34 itself got folded into
`mrm-75` this week), or does Carlos want those done as their own separate pass first? Ask, don't
assume — this materially changes the size of the work.
