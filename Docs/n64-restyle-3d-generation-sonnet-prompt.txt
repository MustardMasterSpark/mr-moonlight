TRAPS FOUND THIS SESSION — browser automation via Claude in Chrome + Tripo
===========================================================================

These cost real time/credits to discover. Don't repeat them.

1. **Chrome's native "Save As" dialog cannot be seen or clicked by browser automation tools.**
   If Chrome is set to "Ask where to save each file before downloading," every image download
   opens a native OS dialog that the extension has no access to — it just hangs forever, and a
   stray keypress can even re-trigger a duplicate download. Fix (one-time, already done by
   Carlos): `chrome://settings/downloads` → turn OFF "Ask where to save each file before
   downloading." After that, downloads land silently in `C:\Users\calva\Downloads\` as
   `image_0.png`...`image_3.png`, which a script then moves+renames into the right character
   folder. **This setting should already be off from this session — verify before assuming it's
   still off if downloads seem to hang.**

2. **Tripo's reference-image upload is additive, not a replace.** Uploading a new character's
   turnaround does NOT clear the previous character's reference — both stack as thumbnails, and
   the model silently used the OLD (first) one for at least one generation this session (wasted a
   batch on a duplicate Devil instead of Clown). Fix: after every upload, **click the small delete
   ✕ on the stale thumbnail** (hover reveals it, top-right corner of the thumbnail, roughly
   (116, 193) in a 1568-wide viewport at the panel's default scroll position) and **visually
   verify only one thumbnail remains** before clicking Generate. Zooming into that region with the
   `zoom` action is the fastest check.

3. **A worse failure mode: NO reference attached at all, with no visible error.** At one point the
   file input's element reference had gone stale (a `find`/`read_page` ref pointed at a detached
   DOM node) and the upload silently did nothing — no thumbnail appeared, and the resulting
   generation ignored the character entirely, inventing an unrelated design from the text prompt
   alone. Symptom: the reference-thumbnail area is completely empty, not just showing the wrong
   character. **Always re-verify the thumbnail is present (not just "the right one") right after
   upload, especially after any batch that failed or returned an unexpected error** — stale refs
   tend to cluster right after a delete/DOM-mutation, so a fresh `find` call for the file input
   before re-uploading is worth the extra round-trip if anything upstream looked off.

4. **Element refs (from `find`/`read_page`) go stale often on this page** — new generations
   prepending to the feed, or a delete-confirmation modal, both mutate enough DOM that a ref from
   even one action ago can 404. Cheap fix: re-run `find` for the textbox/file-input by description
   rather than trusting a cached ref number across more than one or two actions.

5. **Aspect ratio must be set per-view, not per-character**: FRONT/BACK = 1:1, LEFT/RIGHT = 3:4.
   Easy to forget when batching — the aspect-ratio buttons don't reset between generations, so if
   you go FRONT → LEFT without explicitly clicking 3:4, it silently generates LEFT at 1:1 instead.

6. **Scroll position drifts as new generations prepend to the feed.** The download icon for "the
   batch I just generated" is only at a fixed y-coordinate if you're scrolled to the very top.
   Always `scroll` to top immediately before clicking the download icon, or you'll download (or
   worse, delete) the wrong batch. This bit me once — clicked what I thought was the download
   button on the newest batch but the feed had scrolled and it opened a lightbox on an older image
   instead.

7. **`form_input` (not `computer` type-simulation) is the fast way to fill the prompt textarea.**
   The prompts are ~5,000 characters; simulated keystrokes would be far slower and more failure-
   prone. `form_input` sets the value directly and worked reliably all session.

8. Generation time: **GPT Image 2 took roughly 60–90 seconds per 4-image batch**; budget waits
   accordingly (used repeated 10s `wait` calls in `browser_batch`, checking with a screenshot every
   30s). Nano Banana Pro was similar.
