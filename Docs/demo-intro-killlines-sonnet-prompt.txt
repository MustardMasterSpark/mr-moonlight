**8. A REAL, pre-existing gameplay bug found and fixed** (Carlos noticed it while testing this
session's build, unrelated to the UI work above — flagged as "red tint never clears after
health regen"):

**Root cause:** `HealthRegenDebugToggle.OnDamaged` fires *synchronously* inside
`PlayerDamageReceiver.TakeDamage`, i.e. in the exact same call where damage lands on
PolymindGames' HealthManager — which is BEFORE `MoonlightPlayerRig`'s next `Update()` mirrors
that hit into `PlayerStats.Health.BaseValue`. So `StartRegenTween()`'s `missing = MaxValue -
stats.Health.BaseValue` always read the STALE, pre-hit (full) health and silently computed
`missing <= 0` → returned immediately, every single time. The hit-triggered "wait 2s, then
heal" behavior the component's own doc comment promises has *never* actually worked; only the
manual F5-toggle path worked (it runs on a later Update tick, after the mirror catches up).

**Fix:** added `MoonlightPlayerRig.CurrentHealth` (reads HealthManager directly, bypassing the
once-a-frame mirror) and pointed `HealthRegenDebugToggle.StartRegenTween()`'s `missing`
calculation at it instead of the stat mirror.

**Verified live:** damaged the player via script, took NO further action, and both health and
the ScreenTint "HealthDamage" contribution returned to full/zero within the documented delay —
confirmed via `MrMoonlight.VFX.ScreenTint.RedContributions` read back live, not by eyeballing a
screenshot.

Files: Assets/_Project/Code/Runtime/Player/MoonlightPlayerRig.cs (new `CurrentHealth` prop),
HealthRegenDebugToggle.cs (StartRegenTween's `missing` calc).

TRAPS FOUND THIS SESSION — READ BEFORE DOING SIMILAR MCP/UI WORK
===========================================================================

1. **manage_gameobject `create` under a Canvas breaks CanvasScaler inheritance.** HUD Canvas's
   own Transform.localScale is 0.632 (that's how "Scale With Screen Size" actually works in
   this project — NOT sizeDelta manipulation). `create` parents new children with
   worldPositionStays=true by default, so Unity auto-compensates the new child's localScale to
   cancel the parent's 0.632 and preserve "world scale 1" — which is exactly wrong for a UI
   RectTransform. Every normal HUD sibling (System Message, etc.) has lossyScale 0.632; a
   freshly `create`d one gets lossyScale 1.0, renders ~1.6x too big, and can end up positioned
   entirely off-screen (this is EXACTLY what happened: the letterbox bars were invisible on
   first build because of this, not because anything else was wrong). **Fix: after `create`ing
   any new top-level child of a CanvasScaler'd Canvas, explicitly set `transform.localScale =
   Vector3.one`** (matches every sibling). Cheapest via execute_code, not manage_gameobject
   modify (see #4).

2. **TMP `alignment` enum: 1026 is Center+Bottom, not Center+Middle.** (1024=Bottom,
   512=Middle, 256=Top for vertical; 2=Center horizontal.) 514 = Center+Middle. Don't copy an
   existing element's alignment value without checking what it actually decodes to for your
   layout — System Message's 1026 is correct FOR System Message (bottom-anchored single line),
   wrong for a box you want text vertically centered in.

3. **manage_camera screenshot cannot be trusted for Screen Space Overlay UI in this
   environment** — it reported "camera: PlayerCamera" and consistently excluded the HUD Canvas
   even without a `camera` param passed. Matches the already-known memory
   (mrm11_event_director_traps.md: "MCP screenshots can drop overlay UI"). **Verify UI state by
   reading component data back (CanvasGroup.alpha, RectTransform.GetWorldCorners, etc.) via
   execute_code/resource reads, not by trusting a screenshot** — though once the scale bug (#1)
   was fixed, screenshots DID start showing the UI correctly, so they're not universally
   broken, just not reliable as the first line of verification.

4. **`manage_gameobject action=modify` (e.g. set_active) is blocked during Play Mode** ("This
   cannot be used during play mode") and **target resolution needs `search_method: "by_id"`**
   when passing a raw instance ID as target, or it tries name-matching first and fails.

5. **Instance IDs do NOT survive a scene reload or domain reload.** Re-resolve every
   GameObject/component by path (`find_gameobjects` with `by_path`, or `GameObject.Find` in
   execute_code) after any `refresh_unity`, `EditorSceneManager.OpenScene`, or Play Mode
   enter/exit if you cached IDs from before it.

6. **`manage_scene action=load` can spuriously report "Current scene has unsaved changes"**
   immediately after a successful `save` (saw this repeatedly, correlated with domain reloads
   re-touching the scene's dirty flag). Reliable workaround:
   `UnityEditor.SceneManagement.EditorSceneManager.OpenScene(path,
   OpenSceneMode.Single)` via execute_code, after confirming via `git status --short` that a
   save didn't actually change anything on disk (it didn't, in this case — pure noise).

7. **Two `PlayerDamageReceiver` components exist on the player** — one on `Player_Tracey`
   (root, the one real shots actually hit, per the collider parent-chain) and one on
   `MrMoonlight Systems` (child). The class's own doc comment says putting one on Systems is
   WRONG ("every shot would pass straight through"). It appears unused/dead but I did NOT
   remove it — didn't confirm nothing else references it, and it wasn't in scope for what
   Carlos asked. **Worth asking Carlos before deleting it** — flagging, not fixing.
