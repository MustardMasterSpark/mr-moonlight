3. ⚠ THE FIVE PRECAUTIONS THAT WILL BITE YOU
==============================================================================

3.1 NEVER WRITE DIRECTLY TO PlayerStats HEALTH OR STAMINA
    PolymindGames' HealthManager/StaminaManager own those now. `MoonlightPlayerRig` mirrors them
    into `PlayerStats` EVERY FRAME. Any `stats.Health.Deplete(...)` or `.BaseValue = x` is
    silently erased on the next tick — no error, no warning, it just does nothing.

    This single mistake caused THREE separate reported bugs this session (enemies couldn't hurt
    the player, health-regen cheat dead, infinite-stamina cheat dead).

    Use instead:  rig.ApplyIncomingDamage(amount, args)   -- damage, applies Defense
                  rig.RestoreHealth(amount)               -- healing
                  rig.RestoreStamina(amountOn0to100Scale) -- stamina
    `Stat.Lock()` DOES work — the mirror was taught to respect locked stats and push them the
    other way. MRM-41's consumables have NOT been converted yet and will hit this (§6).

3.2 THE PREFAB BUILD TOOL WILL BREAK THE SCENE IF RE-RUN
    `Tools > MrMoonlight > Migration > Build Player_Tracey from FPS_Player (MRM-9)` DELETES and
    recreates the prefab asset, which breaks the link from the instance in `Island.unity`.
    Only re-run it if you are prepared to re-instantiate the player in the scene and re-point
    `Event Director.player`. Day-to-day edits should go on the prefab directly.

3.3 EDITING A PREFAB ASSET NEEDS PrefabUtility, NOT SetDirty
    `LoadMainAssetAtPath` + `SetDirty` + `SaveAssets` silently does NOT persist changes to a
    prefab's own hierarchy (it only saves nested prefab instances). Use
    `PrefabUtility.LoadPrefabContents` → `SaveAsPrefabAsset` → `UnloadPrefabContents`.
    Also: `SaveAsPrefabAsset` returns SUCCESS while writing nothing if Unity holds a filesystem
    lock on the folder (the tell is `rm` failing with "Device or resource busy"). Delete/modify
    through `AssetDatabase.DeleteAsset`. ALWAYS verify by re-reading the asset.

3.4 LAYERS ARE LOAD-BEARING AND NON-OBVIOUS
    FPSCore hardcodes layer indices; eight collided with ours and were moved to 18–25.
    Full table in the integration doc §4. Three that matter most:
      - Player root MUST be on `Player`(3) — Blaze AI vision looks for that layer. Vendor
        default was `Character`(25), which made the player invisible to every enemy.
      - Enemy damage hitboxes are on `Health`(10). `Enemy`(6) is deliberately NOT in the weapon
        damage mask, because the enemy's root Blaze capsule sits on it, encloses all 15 hitboxes
        and has no damage handler — shots stopped on it and did nothing.
      - Ragdoll bones are on `Ragdoll`(26), outside the weapon mask, so shots pass through them.
    If shots stop doing damage again, check layers before anything else.

3.5 VENDOR DEFAULTS ARE TUNED FOR THE VENDOR'S DEMO, NOT OUR GAME
    Four separate bugs this session were vendor defaults that are perfectly sensible in the HQ FPS
    firing-range demo and wrong here: a PostProcessing-only camera volume mask, a mouse-shaped
    input release test, cursor lock parked on a GameMode prefab we didn't take, and Temporal AA
    (which smears our pixel dither). When migrating anything else from this asset, audit its
    assumptions, not just its references.

8. PERFORMANCE — MEASURED, WITH THE BIG WIN NOT YET TAKEN
==============================================================================

Baseline ~105 FPS, CPU main-thread bound (8.68 ms main vs 6.86 ms GPU).
NOTHING added by MRM-9 allocates per frame; no leaks (all subscriptions released in OnDestroy).

Both dominant costs are PRE-EXISTING and scale with MRM-34's 102-Spotter population:
  - 2,762 active kinematic ragdoll bodies → Physics.SyncColliderTransformBatchJob = 5.75 ms
  - 168 KB GC per frame across 968 allocations — ~89% is Blaze AI (drops to 19 KB without them)

APPLIED: Temporal AA → None. Cost ~1 ms AND it smears the pixel dither RetroLit exists to make.

NOT APPLIED, biggest available win — gate the ragdolls. Measured: 2,762 → 758 bodies,
5.75 → 1.71 ms, ~105 → ~117 FPS. Not shipped because Blaze drives KNOCKDOWN through the same
ragdoll (`HitStateBehaviour`), so the re-enable path must cover non-fatal knockdown as well as
death, and both need deliberate testing. This belongs to MRM-34's owner.

The GC churn matters more than average FPS — 168 KB/frame causes collection stutter regardless.
Best lever is fewer simultaneously-active Spotters or distance-based deactivation.

CAVEAT: these are EDITOR numbers and are inflated. Ratios hold; confirm absolutes on build 24.
