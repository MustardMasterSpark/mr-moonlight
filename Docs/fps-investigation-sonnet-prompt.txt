CURRENT TASK: FPS-cap investigation — mostly resolved, one real thread left dangling
===========================================================================
Carlos noticed the Editor running far faster (~163-200 FPS) than the standalone build (looked
"capped" around 75, later 60). Long back-and-forth investigation this session, ruled out with real
evidence (not guesses) in this order — do not re-litigate any of these from scratch:

- Not render cost: FSR on/off gave identical 75 FPS/13.3ms in the build across multiple
  resolutions/quality tiers.
- Not `QualitySettings.vSyncCount` (confirmed 0; only one quality level exists project-wide, no
  hidden per-platform override in ProjectSettings/QualitySettings.asset).
- Not `Application.targetFrameRate` (grepped ALL of Assets/, not just our code; found 4 call sites
  in vendor packages, none attached to anything in any tracked scene/prefab).
- Not the AMD driver (Carlos confirmed live in Adrenalin: VSync/FRTC/Chill/Boost/Enhanced Sync all
  off/correct).
- Not Windows Fullscreen Optimizations (disabled for the exe specifically, no change).
- Not the Graphics API (forced D3D11 via `-force-d3d11`, identical to Auto).

**Root cause, confirmed:** Carlos runs three monitors at three different refresh rates — see memory
`carlos_monitor_layout` for the exact layout (Pantalla 1 "24E4" 60Hz, where Claude Code runs;
Pantalla 2 "Artist 12" 59.94Hz, his file-dump screen; Pantalla 3 "S24D332" 75Hz, his main monitor).
Every "cap" we measured across the whole session matched exactly whichever physical screen the
build window happened to be on at that launch. This is genuine, correct Windows-compositor
vsync-to-display behavior — not a bug, not a shipping concern, and explains why the Editor
comparison was never fair (the Editor Game View doesn't observe the same display-vsync a real
build's window does).

**Not fully closed.** Carlos pointed out he gets ~120 FPS in War Thunder on this exact same
three-monitor, ≤75Hz setup — meaning genuine tearing/uncapped presentation IS achievable on his
hardware when an engine does it right, so display refresh alone isn't the complete story. Checked
`PlayerSettings.useFlipModelSwapchain` (the D3D11 prerequisite for tearing-allowed/uncapped
presents) — already `true` project-wide — yet Exclusive Fullscreen still capped to the display
refresh rate in every test. **The real remaining difference between our build's presentation and
something like War Thunder's has not been found.**

**Next steps, not yet done — pick up here:**
1. Ask Carlos to install RTSS (RivaTuner Statistics Server, free, ships with MSI Afterburner). It
   hooks actual present calls, independent of everything tested so far, and can show real frame
   timing plus visually confirm whether tearing is occurring at all.
2. Get an apples-to-apples comparison: is War Thunder's 120 FPS specifically in TRUE Exclusive
   Fullscreen mode (not Borderless)? If War Thunder itself also caps to refresh rate in its own
   Borderless/Windowed modes, that's expected and consistent — the real test is Exclusive vs.
   Exclusive.
3. If RTSS shows Mr. Moonlight genuinely isn't getting a tearing-allowed present even in Exclusive
   Fullscreen with D3D11 + flip-model swapchain already on, the next research direction is Unity's
   own DXGI present-flag handling for `FullScreenMode.ExclusiveFullScreen` specifically — whether it
   actually passes `DXGI_PRESENT_ALLOW_TEARING` on Present() calls, or whether Unity 6.3's Windows
   Player only uses that path in Windowed/Borderless and always vsyncs true Exclusive. This may
   need an actual Unity forum/release-notes check, not just PlayerSettings reflection (already
   exhausted what reflection alone can tell us — `useFlipModelSwapchain` and
   `vulkanNumSwapchainBuffers` were the only tearing/sync-related PlayerSettings properties found).
4. Consider testing on different hardware if Carlos has access to any (a laptop, a friend's PC) —
   if the same build runs uncapped elsewhere, the remaining piece is specific to this one machine's
   environment, not the project.
